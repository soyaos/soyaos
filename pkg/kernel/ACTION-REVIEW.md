# Optional per-action semantic review

A Pack can declare `review_handler: prompts/review_action.md` alongside an action's `handler`. The file is loaded when registering the Pack. Missing, empty and nonlocal review paths fail registration. Packs without this field keep the existing single-generation behavior.

The review uses the action's resolved provider/model and the same action timeout. It receives `{action_id: <selected action>, request: <original row request>, draft: <generated Markdown>}` and its own system prompt. The action ID distinguishes a post from a video even when the original business brief prefers video. The original request includes the effective title and persisted business context; failed drafts are not promoted into the original evidence. Reviewed generation uses temperature 0.2 and review uses 0.1; unreviewed legacy generation retains its existing sampling behavior.

An optional `plan_handler: prompts/plan_post.md` creates an editorial plan once before generation. It requires `review_handler`, uses the same model/timeout, and rejects missing, empty or nonlocal prompt files and empty plan results. The plan is supplied as `editorial_plan` to generation and any repair, but is deliberately absent from the review evidence. It cannot supply new facts. EstateMuse uses this for posts; videos skip planning.

Every draft receives both deterministic text validation and semantic review, so a single repair receives all known issues together. The reviewer returns `checks`, `approved`, and `findings`. Checks cover exactly five IDs: `business_context`, `factual_claims`, `method_logic`, `format`, and `safety`; each contains a boolean `passed` and a nonempty evidence-based `reason`. Approval must equal the conjunction of those checks. Approved drafts have empty findings; rejected drafts require findings with an exact draft `quote` and a specific correction in `reason`. Missing or duplicate checks, contradictory decisions, unknown fields, trailing JSON, ungrounded excerpts and upstream errors fail closed. Responses must be plain JSON. Provider responses are not dumped into errors on protocol failures. These checks constrain the protocol, not the truth of the model's assessments.

Review calls request upstream `response_format: json_schema` with `strict: true` and no additional properties at any object level. Draft and planning calls do not acquire a response schema. The runtime still checks five unique dimensions, decision consistency, nonempty reasons and exact draft excerpts: schema output cannot prove any of these semantic relationships. Unsupported requests may fail or be silently ignored upstream; the runtime never weakens validation or retries without the schema. In a real probe asking for a contradictory string value and extra field, the configured qwen3.6-plus returned HTTP200 with both violations, while account-available qwen3.8-max-0902 followed the boolean-only schema. API acceptance is not enforcement evidence. See [Alibaba's structured-output documentation](https://docs.modelstudio.console.alibabacloud.com/en/model-studio/qwen-structured-output) for model-specific support. JSON Object mode alone would not constrain extra fields. No global model setting was changed by these probes.

Optional `text_validation.mirror_table` validates a Markdown table under its named `section`. Its `column` must contain exactly `rows` nonempty cells whose concatenation equals the source `text_validation.section`, ignoring whitespace only. EstateMuse videos require three narration rows matching the full narration. This catches missing or changed narration independently of the model; it does not assess factual accuracy.

Text and semantic failures share `text_validation.max_repairs` (zero if text validation is absent). A rejected draft feeds all findings into the existing repair request; the repaired draft is checked again. The loop does not reset its budget or timeout for review. With one repair there are at most two draft generations and two reviews, plus one planning call if enabled, excluding the existing transport EOF retry behavior. If validation still fails, no successful ActionResult is returned. The original row remains unchanged.

Successful reviewed actions include `output.semantic_review: "passed"`; unreviewed legacy actions omit it. A caller requiring review must check this marker, since an older runtime may ignore unknown manifest fields. Deploy the supporting runtime before enabling the Pack field. The private EstateMuse trial helper requires the marker.

This is model-based evidence review, not browsing, external fact verification or human publishing approval. A model can miss errors or reject a good draft. Keep representative negative and positive evaluation cases, and retain human product acceptance.

Verification:

```sh
go test -race -count=1 ./pkg/kernel/... ./pkg/soyapack/... ./pkg/openaicompat/... ./pkg/llmcall/...
```

Optional real-provider evaluation uses `SOYA_ACTION_REVIEW_FIXTURES` pointing to a private JSON file with `prompt` and `cases` (`name`, optional `action_id`, `request`, `draft`, `approved`, optional `text_validation`). Supply the usual SOYA_MODEL environment securely, then run `go test -v -count=1 ./pkg/kernel/... -run '^TestActionReviewRealFixtures$'`. This makes real provider calls. Fixtures are not checked into the repo; logs include case names, verdict matches and elapsed time, not drafts or credentials. Optional `SOYA_ACTION_REVIEW_REPORT` saves rejection details to a private 0600 JSON file for debugging, distinguishing `model_approved` from the combined text/semantic verdict. Passing this finite fixture set does not prove universal semantic accuracy.

For compatible providers, optional `SOYA_MODEL_THINKING_BUDGET` (1–32768) sends `thinking_budget`; unset or invalid values omit the field. It does not change the action timeout or enable thinking itself. The private trial's 512-token experiment still exceeded its 60-second action deadline; no default model or thinking configuration was changed.

The opt-in evaluation's private report also retains `review_responses`, including explicit assessments for approved drafts. This helps diagnose false approvals. It captures response text only, not request headers or reasoning tokens; assessments can quote draft content, so keep this report private. Production action logs do not acquire this capture behavior.

Review assessments use the draft's language and preserve event terms rather than translating them into assumed synonyms. EstateMuse's prompt defines reporting, acceptance, arrival, actual work start, and completion separately. This is a review instruction, not a deterministic guarantee that the model applies those definitions correctly.

The schema's finding `quote` enum is built per invocation from unique, nonempty trimmed lines of the actual draft. Each candidate remains an exact substring of that draft. This prevents a schema-enforcing provider from inventing or shortening its citation; it may select a longer line and explain the particular issue in `reason`. Empty drafts fail before the review call. Runtime substring validation remains in place for providers that ignore schema constraints. Selecting a real source line does not prove the associated judgment is correct.
